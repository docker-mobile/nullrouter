  * `overhead` is the router's cost. `direct` is the mock's own service time and should

    the overhead column is not trustworthy.
  * If overhead lands on a round fraction of --mock-sleep-ms, suspect the harness rather
    than celebrating the result: it is probably timing the mock.

  * S5 is the headline: per-frame cost multiplies, and it is the shape real agent traffic
    takes.

Why this run exists, and why the change it measured was reverted
----------------------------------------------------------------
Pingora's `threads` defaults to 1 and the gateway is the only public port, so every request went
through one worker. Against a zero-latency mock that is a real ceiling: 98% of one core, plateauing
at 7013 req/s while the runtime behind it still reached 11605. Raising threads to the core count
lifted throughput to 8788 req/s (+25%). This run is that configuration.

It was reverted. Two reasons, both measured:

  1. The ceiling is unreachable in real use. The same c=64 load against a 250ms mock -- a realistic
     provider -- leaves the gateway at 3% of one core. Provider latency dominates by two orders of
     magnitude.

  2. The threads cost latency on every request. Against the `fair` run:
       S1 c=8  1.606 -> 1.832 ms  (+14.1%, ranges [1.604..1.676] vs [1.753..1.871], not overlapping)
       S2 c=8  1.656 -> 1.811 ms  (+9.4%)
       S6 c=1  1.296 -> 1.500 ms  (+15.7%)
     Other cells moved the other way by less, so the picture is mixed -- but the non-overlapping
     ranges at c=8 are a real cost, not noise.

Kept as `NULLROUTER_GATEWAY_THREADS` (default 1, or `cores`, or a number) for the case where the
upstream really is that fast -- a local model on the same box -- and the tradeoff inverts.

The headline figures come from 20260830T185309Z-nullrouter-fair, not this run.
